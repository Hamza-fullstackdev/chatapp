IMPORTANT ARCHITECTURAL RULE
==================================================

SQLite is NOT the central database.

SQLite is LOCAL to each user's device.

Supabase PostgreSQL is the permanent server-side source of truth.

For example:

User A:

Expo
 -> SQLite A
 -> Socket.IO
 -> Node.js
 -> Supabase PostgreSQL

User B:

Node.js
 -> Socket.IO
 -> SQLite B
 -> UI

If User B is offline:

User A
 -> Node.js
 -> PostgreSQL

When B comes online:

B
 -> Sync API
 -> Node.js
 -> PostgreSQL
 -> SQLite B
 -> UI

Never attempt to make one user's SQLite database communicate directly with another user's SQLite database.

==================================================
OFFLINE-FIRST ARCHITECTURE
==================================================

The application MUST be offline-first.

SQLite should contain local copies of:

- Users
- Conversations
- Conversation members
- Messages
- Message attachments
- Message reactions
- Local sync state
- Sync queue

The UI should primarily read from SQLite for chat screens.

Do NOT make the chat screen wait for the network before displaying locally available messages.

When the user sends a message:

1. Generate a UUID on the mobile client.
2. Insert the message into SQLite immediately.
3. Display it optimistically.
4. Add an operation to sync_queue.
5. If online, synchronize immediately.
6. If offline, keep the operation pending.
7. When connectivity returns, synchronize automatically.

Example:

messages:

id = UUID
conversation_id
sender_id
client_message_id
type
text
status
created_at

sync_queue:

id
operation
entity_id
payload
status
retry_count
created_at

SYNC SYSTEM
==================================================

Create a dedicated mobile SyncEngine.

Suggested structure:

services/
  sync/
    SyncEngine.ts
    SyncQueue.ts
    MessageSync.ts
    ConversationSync.ts
    SyncState.ts

The SyncEngine must support:

- Offline queueing
- Batch synchronization
- Retry
- Exponential backoff
- Idempotency
- Duplicate protection
- Upload/download synchronization
- Connection recovery
- Sync cursor
- Partial failures

Do NOT create one HTTP request per message if multiple messages are pending.

Example:

POST /api/sync

{
  "operations": [
    {
      "operation": "CREATE_MESSAGE",
      "clientMessageId": "...",
      "conversationId": "...",
      "payload": {}
    },
    {
      "operation": "CREATE_MESSAGE",
      "clientMessageId": "...",
      "conversationId": "...",
      "payload": {}
    }
  ]
}

The server should process the batch safely using PostgreSQL transactions where appropriate.

The synchronization API MUST be idempotent.

A retry must never create duplicate messages.

Use client-generated UUIDs / client_message_id with a unique database constraint.
